# 🐳 CoreTech 애플리케이션 부하 테스트 분석 보고서

## 📝 최종 결과 요약
- 안정적 처리 가능 부하: **300명 동시 사용자**, **3000 요청**
- 400명 이상 조건에서는 **단일 워커 프로세스 병목**으로 실패
- CPU는 여유(Idle ~81%), **소프트웨어 실행 구조 문제** 확인됨

---

## 1. 개요
Docker 기반 `coretech` 애플리케이션의 성능 한계점 파악을 위해 부하 테스트를 진행하였다.

---

## 2. 테스트 및 분석 과정

### 🧪 테스트 1: 기준 성능
- **조건:** 100 동시 사용자 / 1000 요청  
- **결과:** 성공 ✅ (초당 ~49 요청 처리)  

> 💬 결과 분석: 기본 구조에서 무리 없이 요청 처리 가능 → **애플리케이션 및 DB 초기 설정은 정상 작동하는 상태**로 판단됨.  

---

### 🧪 테스트 2: 고부하 (1차)
- **조건:** 400 동시 사용자 / 4000 요청  
- **결과:** 실패 ❌ (1912 요청 처리 후 `Connection reset by peer`)  
- **백엔드 로그:** `sqlalchemy.exc.TimeoutError`  

> 💬 결과 분석: **DB 연결 풀 크기 부족**으로 판단됨. 다수의 동시 연결 시 풀 소진 → 응답 지연 및 연결 강제 종료 발생.  

---

### 🛠 조치 1: DB 풀 크기 증가
- `pool_size=50`, `max_overflow=100` 적용  

---

### 🧪 테스트 3: 고부하 (2차)
- **조건:** 400 동시 사용자 / 4000 요청  
- **결과:** 실패 ❌ (3796 요청 처리 후 실패)  

> 💬 결과 분석: DB 풀 확장은 효과 있었음(처리량 ↑) 그러나 여전히 **서버 측 연결 끊김 현상 지속** → DB 병목은 완화, 다른 원인 존재 가능성 제기.  

---

### 🛠 조치 2: Uvicorn 타임아웃 증가
- 실행 옵션: `--timeout-keep-alive 65`  

---

### 🧪 테스트 4: 고부하 (3차)
- **조건:** 400 동시 사용자 / 4000 요청  
- **결과:** 실패 ❌ (`Timeout specified has expired`)  

> 💬 결과 분석: **클라이언트 타임아웃 초과**로 판단됨. 서버 응답 지연이 계속 발생 → 타임아웃만 늘려도 구조적 병목이 해소되지 않음.  

---

### 🧪 테스트 5: 검증 (ab 벤치마크)
- **조건:** 300 동시 사용자 / 3000 요청  
- **결과:** 성공 ✅  

> 💬 결과 분석: **300명 수준까지는 안정적으로 처리 가능** → 하드웨어 리소스 문제 아님, **애플리케이션 실행 구조(단일 워커)**가 근본 원인으로 좁혀짐.  

---

## 3. 자원 모니터링 결과
- `sar` 분석: CPU idle 평균 **81.5%**  
- 서버는 여유가 충분했음 → **멀티코어 활용이 안 된 단일 워커 구조 문제** 확정.  

---

## 4. 최종 결론 및 권장 해결책
- 현재: **Uvicorn 단일 워커 → CPU 1개만 사용**
- 개선: **Gunicorn 프로세스 매니저** 사용, 멀티 워커로 코어 활용
