# 2-3-8: 자원 제한/격리 (`ulimit`, `cgroups` 개요, OOM Killer)

안정적인 시스템 운영을 위해서는 특정 사용자나 프로세스가 시스템의 자원(CPU, 메모리, 파일 등)을 과도하게 사용하여 다른 프로세스나 시스템 전체에 영향을 미치는 것을 방지해야 합니다. 리눅스는 이를 위한 여러 메커니즘을 제공합니다.

## 1. `ulimit`: 셸 세션의 자원 제한

- **기능**: `ulimit` (user limit) 명령어는 현재 셸 세션과 그 자식 프로세스들이 사용할 수 있는 자원의 상한선을 설정하거나 확인하는 데 사용됩니다. 이는 주로 시스템에 로그인한 사용자가 생성할 수 있는 프로세스 수나 열 수 있는 파일 개수 등을 제한하여 시스템을 보호하는 역할을 합니다.

- **주요 옵션 및 사용법**:
    - **모든 제한 사항 확인**:
      ```bash
      ulimit -a
      ```
    - **소프트(Soft) 제한과 하드(Hard) 제한**:
        - **소프트 제한**: 일반 사용자가 스스로 높일 수 있는 현재 적용되는 제한 값. 하지만 하드 제한을 초과할 수는 없습니다.
        - **하드 제한**: 루트 사용자만 설정할 수 있는 절대적인 상한선. 소프트 제한은 이 값을 넘을 수 없습니다.
        - `ulimit -S`는 소프트 제한, `ulimit -H`는 하드 제한을 의미합니다.

- **자주 사용되는 제한 항목**:
    - `ulimit -n`: 열 수 있는 파일 디스크립터(File Descriptor)의 최대 개수 (open files). 서버 프로그램은 많은 동시 연결을 처리하기 위해 이 값을 높여야 하는 경우가 많습니다.
    - `ulimit -u`: 한 사용자가 생성할 수 있는 프로세스의 최대 개수 (max user processes).
    - `ulimit -s`: 스택 크기 (stack size).
    - `ulimit -c`: 코어 파일의 최대 크기 (core file size). 프로그램 비정상 종료 시 생성되는 디버깅용 파일입니다.

- **제한 값 변경**:
  ```bash
  # 현재 세션에서 열 수 있는 파일 개수를 4096으로 늘림 (소프트 제한)
  ulimit -n 4096
  ```

- **영구적인 설정**: `ulimit`으로 변경한 값은 현재 셸 세션에만 유효합니다. 시스템 전체에 영구적으로 적용하려면 `/etc/security/limits.conf` 파일을 수정해야 합니다.
  - 예시: `/etc/security/limits.conf`
    ```
    # <domain> <type> <item> <value>
    *        soft  nofile 10240
    *        hard  nofile 65536
    ```
    (모든 사용자에 대해 열린 파일의 소프트 제한을 10240으로, 하드 제한을 65536으로 설정)

## 2. `cgroups`: 프로세스 그룹의 자원 통제

- **기능**: `cgroups` (Control Groups)는 프로세스들의 그룹에 대해 시스템 자원(CPU, 메모리, 네트워크 대역폭, I/O 등)의 사용을 제한하고 격리하는 강력한 커널 기능입니다. `ulimit`이 사용자 세션 단위의 비교적 단순한 제한을 제공한다면, `cgroups`는 특정 서비스나 애플리케이션(프로세스 그룹)에 대해 훨씬 더 정교하고 세밀한 자원 할당 및 제어를 가능하게 합니다. **컨테이너 기술(Docker, Kubernetes 등)의 핵심 기반**이 바로 이 `cgroups`입니다.

- **주요 서브시스템(컨트롤러)**:
    - `cpu`: CPU 사용 시간을 할당하고 제한합니다. (예: 특정 그룹은 CPU의 20%만 사용)
    - `memory`: 메모리 사용량을 제한합니다. (예: 특정 그룹은 최대 512MB 메모리만 사용)
    - `blkio`: 블록 장치(디스크 등)의 입출력 대역폭을 제한합니다.
    - `pids`: 그룹 내에서 생성할 수 있는 프로세스(PID)의 수를 제한합니다.

- **`systemd`와 `cgroups`**: 현대 리눅스에서는 `systemd`가 `cgroups`를 자동으로 관리하고 사용합니다. 모든 `systemd` 서비스 유닛은 자신만의 `cgroup` 내에서 실행되므로, `.service` 파일에 간단한 지시어를 추가하여 자원을 쉽게 제한할 수 있습니다.

  - 예시: `my-app.service` 유닛 파일에서 메모리 사용을 500MB로 제한
    ```ini
    [Service]
    ExecStart=/usr/bin/my-app
    MemoryLimit=500M
    CPUQuota=20%
    ```

## 3. OOM Killer: 최후의 수호자

- **기능**: OOM (Out-of-Memory) Killer는 시스템의 메모리가 부족하여 커널이 더 이상 정상적으로 동작할 수 없는 비상 상황에 처했을 때, 시스템 전체의 다운을 막기 위해 특정 프로세스를 강제로 종료시키는 커널의 메커니즘입니다.

- **동작 원리**:
    1.  시스템 메모리가 임계점 이하로 떨어지면 OOM Killer가 활성화됩니다.
    2.  실행 중인 모든 프로세스에 대해 `oom_score`라는 점수를 계산합니다.
        - 점수가 높을수록 종료될 확률이 높습니다.
        - 점수는 주로 프로세스가 사용 중인 메모리 양에 비례하며, 다른 요소(실행 시간, 루트 권한 여부 등)도 고려됩니다.
    3.  가장 높은 `oom_score`를 가진 프로세스를 찾아 `SIGKILL` 시그널을 보내 강제 종료시킵니다.

- **OOM Killer 확인**: 커널 로그(`dmesg` 또는 `journalctl -k`)를 확인하면 OOM Killer가 동작한 기록을 볼 수 있습니다.
  ```
  [... dmesg ...]
  Out of memory: Kill process 12345 (some_process) score 850 or sacrifice child
  Killed process 12345 (some_process) total-vm:..., anon-rss:..., file-rss:..., shmem-rss:...
  ```

- **`oom_score` 조정**: `/proc/[PID]/oom_score_adj` 값을 조정하여 특정 프로세스가 OOM Killer에 의해 종료될 확률을 높이거나 낮출 수 있습니다. (예: -1000으로 설정하면 거의 종료되지 않음)

이러한 자원 제한 및 관리 도구들은 멀티태스킹 환경에서 시스템의 안정성과 공정성을 보장하는 데 핵심적인 역할을 합니다.
