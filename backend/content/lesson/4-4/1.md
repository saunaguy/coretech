# 4-4-1: 로드밸런서/프록시 기본: L4/L7, 헬스체크, 세션 유지

웹 서비스의 사용자가 늘어나면 서버 한 대로 모든 트래픽을 감당하기 어려워집니다. **로드밸런서(Load Balancer)**는 여러 대의 서버(백엔드 서버)를 마치 하나의 서버처럼 동작하게 만들어, 들어오는 트래픽을 여러 서버에 적절히 분산시켜주는 핵심적인 스케일 아웃(Scale-out) 기술입니다. 로드밸런서는 동작하는 계층(Layer)에 따라 크게 L4와 L7으로 나뉩니다.

## 1. L4 로드밸런서 vs L7 로드밸런서

### L4 로드밸런서 (Transport Layer)
- **동작 방식**: 전송 계층(TCP/UDP, OSI 4계층)의 정보, 즉 **IP 주소와 포트 번호**를 보고 트래픽을 분산합니다. 패킷의 내용(HTTP 헤더, URL 등)은 들여다보지 않고, 단순히 들어온 TCP/UDP 연결을 백엔드 서버 중 하나로 전달(포워딩)하는 역할만 합니다.
- **장점**:
    - 패킷 내용을 분석하지 않으므로 처리 속도가 매우 빠릅니다.
    - TCP/UDP 기반의 모든 서비스(HTTP, FTP, SMTP 등)에 적용할 수 있습니다.
- **단점**:
    - 패킷 내용을 보지 못하므로, URL 경로, HTTP 헤더 등 애플리케이션 레벨의 정보를 기반으로 한 정교한 부하 분산이 불가능합니다.
- **종류**: LVS(Linux Virtual Server), HAProxy(TCP 모드), AWS NLB(Network Load Balancer)

### L7 로드밸런서 (Application Layer)
- **동작 방식**: 응용 계층(HTTP, OSI 7계층)의 정보, 즉 **HTTP 헤더, URL, 쿠키 등**을 보고 트래픽을 분산합니다. 클라이언트와 로드밸런서 간에 TCP 연결을 맺고, 다시 로드밸런서와 백엔드 서버 간에 새로운 TCP 연결을 맺는 **프록시(Proxy)** 방식으로 동작합니다.
- **장점**:
    - 요청의 내용을 분석할 수 있으므로, 매우 정교하고 유연한 부하 분산 정책을 설정할 수 있습니다.
        - `/images` 경로는 이미지 서버로, `/api` 경로는 API 서버로 분산 (URL 기반 라우팅)
        - 특정 쿠키를 가진 사용자는 특정 서버로 연결 (A/B 테스트)
        - HTTP 헤더를 분석하여 모바일 사용자는 모바일용 서버로 연결
    - SSL Offloading: 클라이언트와의 HTTPS 통신을 로드밸런서가 대신 처리하고, 로드밸런서와 백엔드 서버 간에는 암호화되지 않은 HTTP로 통신하여 백엔드 서버의 부담을 줄여줍니다.
- **단점**:
    - 패킷 내용을 분석하고 새로운 연결을 맺는 과정에서 L4 로드밸런서보다 부하가 높고 속도가 느릴 수 있습니다.
- **종류**: HAProxy(HTTP 모드), Nginx, Apache(mod_proxy), AWS ALB(Application Load Balancer)

## 2. 로드밸런서의 핵심 기능

### 헬스 체크 (Health Check)
- **기능**: 로드밸런서는 주기적으로 백엔드 서버들에게 "살아있는지" 확인하는 요청(**헬스 체크 프로브, Health Check Probe**)을 보냅니다. 이를 통해 정상적으로 응답하는 서버에게만 트래픽을 보내고, 응답이 없거나 오류가 발생하는 서버는 일시적으로 서비스 그룹에서 제외하여 장애가 전파되는 것을 막습니다.
- **방법**:
    - **L4**: 특정 TCP 포트로 연결을 시도(TCP 헬스 체크)하여 성공 여부를 확인합니다.
    - **L7**: 특정 URL(예: `/health`)로 HTTP GET 요청을 보내, 정상적인 HTTP 응답 코드(예: `200 OK`)가 오는지 확인합니다.

### 세션 유지 (Session Persistence / Sticky Session)
- **기능**: 사용자의 첫 번째 요청을 처리한 서버가, 이후의 요청들도 계속해서 처리하도록 보장하는 기능입니다. 이는 사용자의 로그인 정보나 장바구니 내용이 특정 서버의 세션에 저장되는 경우에 필수적입니다.
- **방법**:
    - **Source IP Hash**: 클라이언트의 IP 주소를 해싱하여 특정 서버에 매핑합니다. 가장 간단하지만, 여러 사용자가 동일한 NAT 환경(공유기 등)에 있을 경우 부하가 한쪽으로 쏠릴 수 있습니다.
    - **Cookie-based Persistence**: 로드밸런서가 HTTP 응답에 특정 쿠키(예: 서버 ID)를 삽입하여 보냅니다. 클라이언트는 이후 요청 시 해당 쿠키를 함께 보내고, 로드밸런서는 쿠키 값을 보고 요청을 올바른 서버로 전달합니다. 가장 널리 사용되는 방식입니다.

### 부하 분산 알고리즘
- **Round Robin**: 서버 목록을 순서대로 돌아가며 요청을 분산합니다. 가장 간단하고 일반적인 방식입니다.
- **Least Connections**: 현재 연결 수가 가장 적은 서버에게 다음 요청을 보냅니다. 각 요청의 처리 시간이 다를 때 효과적입니다.
- **Source IP Hash**: 클라이언트의 IP 주소를 해싱하여 결과를 기반으로 서버를 선택합니다. 세션 유지 기능과 관련이 있습니다.

로드밸런서는 단순히 트래픽을 분산하는 것을 넘어, 헬스 체크를 통해 서비스의 가용성을 높이고, 세션 유지를 통해 데이터의 일관성을 보장하며, SSL Offloading 등을 통해 백엔드 인프라의 효율성을 증대시키는 현대적인 웹 아키텍처의 필수 구성 요소입니다.
