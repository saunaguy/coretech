# 3-1-2: 구성 관리: env/시크릿, Drop-in vs 유닛 복제, `Restart=`

안정적이고 재현 가능한 서비스 운영을 위해서는 서비스의 실행 환경과 설정을 체계적으로 관리하는 것이 중요합니다. `systemd`는 환경 변수, 설정 파일 재정의, 자동 재시작 등 강력한 구성 관리 기능을 제공합니다.

## 1. 환경 변수(Environment Variables) 및 시크릿(Secrets) 관리

애플리케이션의 동작에 필요한 설정값(데이터베이스 주소, API 키 등)을 코드에 직접 하드코딩하는 것은 매우 나쁜 습관입니다. `systemd`는 이러한 설정들을 유닛 파일 내에서 관리할 수 있는 여러 방법을 제공합니다.

- **`Environment` 지시어**: 유닛 파일 내에 직접 환경 변수를 설정합니다.
  ```ini
  [Service]
  Environment="DB_HOST=localhost"
  Environment="DB_PORT=5432"
  ExecStart=/usr/bin/my-app
  ```
  - **단점**: 간단하지만, 민감한 정보(비밀번호, API 키)가 유닛 파일에 그대로 노출됩니다.

- **`EnvironmentFile` 지시어**: 환경 변수를 별도의 파일로 분리하여 관리합니다. 이 파일을 적절한 권한(예: `600`)으로 설정하면 민감한 정보를 보호하는 데 더 유리합니다.
  - `/etc/my-app/config.env` 파일:
    ```
    # 데이터베이스 설정
    DB_HOST=db.example.com
    DB_USER=myuser
    DB_PASSWORD="s3cr3t_p@ssw0rd"
    ```
  - `my-app.service` 유닛 파일:
    ```ini
    [Service]
    # 해당 파일의 권한을 600으로 설정하여 보호
    EnvironmentFile=/etc/my-app/config.env
    ExecStart=/usr/bin/my-app
    ```

## 2. 유닛 파일 수정: Drop-in vs 유닛 복제

패키지 관리자(`dnf`, `apt`)를 통해 설치된 서비스의 기본 유닛 파일(보통 `/lib/systemd/system/`에 위치)을 직접 수정하는 것은 좋지 않습니다. 패키지가 업데이트될 때 내가 수정한 내용이 덮어써질 수 있기 때문입니다.

`systemd`는 기본 유닛을 건드리지 않고 설정을 재정의(override)할 수 있는 두 가지 방법을 제공합니다.

### Drop-in 파일 (권장되는 방식)

- **기능**: 특정 유닛의 설정 중 **변경하고 싶은 부분만** 별도의 파일에 작성하여 재정의하는 방식입니다. 원본 유닛 파일은 그대로 두고, 변경 사항만 깔끔하게 관리할 수 있습니다.
- **방법**: `systemctl edit <service_name>` 명령어를 사용합니다.

  ```bash
  # nginx.service의 설정을 변경하고 싶을 때
  sudo systemctl edit nginx.service
  ```
  - 위 명령을 실행하면 `/etc/systemd/system/nginx.service.d/override.conf` 라는 파일이 생성되며 편집기가 열립니다.
  - 여기에 변경하고 싶은 내용만 추가합니다. 예를 들어, `Restart` 정책만 변경하고 싶다면:
    ```ini
    # /etc/systemd/system/nginx.service.d/override.conf
    [Service]
    Restart=always
    ```
- **장점**: 원본 유닛의 내용은 그대로 유지되므로, 패키지 업데이트의 영향을 받지 않으며 변경 사항을 추적하기 쉽습니다.

### 유닛 파일 복제

- **기능**: 원본 유닛 파일 전체를 `/etc/systemd/system/` 디렉터리로 복사한 후, 복사본을 수정하는 방식입니다. `systemd`는 `/etc/systemd/system/`에 있는 유닛을 `/lib/systemd/system/`에 있는 유닛보다 우선적으로 사용합니다.
- **방법**:
  ```bash
  sudo cp /lib/systemd/system/nginx.service /etc/systemd/system/nginx.service
  sudo vi /etc/systemd/system/nginx.service  # 복사본 수정
  ```
- **단점**: 원본의 모든 내용이 복제되므로, 향후 패키지 업데이트에서 원본 유닛 파일에 중요한 변경 사항이 생기더라도 내 복사본에는 반영되지 않아 문제가 발생할 수 있습니다.

**결론**: 대부분의 경우, **Drop-in 파일을 사용하는 것이 훨씬 더 안전하고 관리하기 좋은 방법**입니다.

## 3. `Restart=` 정책: 서비스 자동 복구

`[Service]` 섹션의 `Restart=` 지시어는 서비스 프로세스가 예기치 않게 종료되었을 때 `systemd`가 어떻게 대응할지를 결정하는 중요한 옵션입니다.

- **`no` (기본값)**: 재시작하지 않습니다.
- **`on-success`**: 프로세스가 정상적으로 종료되었을 때(종료 코드 0)만 재시작합니다.
- **`on-failure`**: 프로세스가 비정상적으로 종료되었을 때(0이 아닌 종료 코드, 시그널에 의한 종료 등)만 재시작합니다. **(가장 흔하게 사용)**
- **`on-abnormal`**: 시그널에 의해 종료되었을 때만 재시작합니다.
- **`always`**: 정상/비정상 종료 여부와 관계없이 항상 재시작합니다. (단, `systemctl stop`으로 명시적으로 중지시킨 경우는 제외)

- **`RestartSec=`**: 재시작하기 전에 얼마나 기다릴지를 초 단위로 설정합니다. (예: `RestartSec=5`)

- **예시**: 서비스가 실패하면 5초 후에 자동으로 다시 시작하도록 설정
  ```ini
  [Service]
  ExecStart=/usr/bin/my-daemon
  Restart=on-failure
  RestartSec=5
  ```

이러한 구성 관리 기법들을 활용하면, 각 서비스의 실행 환경을 표준화하고, 예기치 않은 장애로부터 자동으로 복구하며, 시스템 업데이트에 유연하게 대처하는 견고한 서버 운영 체계를 구축할 수 있습니다.
