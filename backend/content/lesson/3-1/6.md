# 3-1-6: 접근 제어: `sudo` 분리, 계정 잠금, MFA/SSH 하드닝

서버 보안의 핵심은 **최소 권한의 원칙(Principle of Least Privilege)**을 지키는 것입니다. 즉, 사용자와 프로세스는 자신의 작업을 수행하는 데 필요한 최소한의 권한만 가져야 합니다. 이를 통해 공격자가 시스템에 침투하더라도 피해를 최소화할 수 있습니다. 여기서는 `sudo` 권한 관리, 계정 보안, 원격 접속 강화를 통한 접근 제어 방법을 알아봅니다.

## 1. `sudo` 권한 분리: `/etc/sudoers.d/`

모든 관리자에게 완전한 `root` 권한을 주는 것은 위험합니다. `/etc/sudoers` 파일을 직접 수정하는 대신, `/etc/sudoers.d/` 디렉터리를 활용하면 사용자별 또는 그룹별로 필요한 `sudo` 권한만 세분화하여 부여하고 관리하기 용이합니다.

- **`visudo`**: `/etc/sudoers`나 그 안의 파일을 편집할 때는 반드시 `visudo` 명령어를 사용해야 합니다. `visudo`는 문법 오류를 자동으로 검사하여, 잘못된 설정으로 인해 `sudo`가 동작하지 않는 치명적인 실수를 방지해 줍니다.

- **시나리오**: `devops` 그룹의 사용자들에게는 `systemctl` 명령으로 웹 서버(`httpd`, `nginx`)를 재시작할 권한만 부여하고 싶다.

- **해결 방법**:
  1.  `sudo visudo -f /etc/sudoers.d/devops-web` 명령으로 새 설정 파일을 엽니다.
  2.  다음 내용을 추가합니다.
      ```
      # devops 그룹은 비밀번호 없이 httpd와 nginx 서비스를 관리할 수 있다.
      %devops ALL=NOPASSWD: /bin/systemctl restart httpd, /bin/systemctl restart nginx
      ```
  - `%devops`: `devops` 그룹을 의미.
  - `ALL=`: 모든 호스트에서.
  - `NOPASSWD:`: 비밀번호 입력 없이 `sudo`를 사용하도록 허용. (자동화 스크립트에 유용)
  - `/bin/systemctl ...`: 허용할 명령어의 전체 경로를 명시.

- **장점**:
    - 역할별로 권한을 분리하여 관리가 명확해집니다.
    - `/etc/sudoers` 주 파일을 건드리지 않아 안전합니다.
    - 사용자나 그룹에 대한 권한 추가/삭제가 해당 파일 하나를 추가/삭제하는 것으로 단순화됩니다.

## 2. 계정 잠금 및 관리

- **`usermod`**: 특정 계정을 잠그거나(lock) 풀(unlock) 때 사용합니다. 퇴사자나 장기 휴가자의 계정을 비활성화하는 데 유용합니다.
  ```bash
  # user01 계정 잠그기 (비밀번호를 만료시켜 로그인 방지)
  sudo usermod -L user01

  # user01 계정 잠금 해제
  sudo usermod -U user01
  ```

- **`passwd`**: 계정의 비밀번호 정책을 관리합니다.
  ```bash
  # user01 계정의 비밀번호 즉시 만료시켜 다음 로그인 시 변경하도록 강제
  sudo passwd -e user01
  ```

## 3. SSH 하드닝(Hardening): 원격 접속 보안 강화

`ssh`는 가장 중요한 원격 관리 통로이므로, 보안을 최대한 강화해야 합니다. 이는 `/etc/ssh/sshd_config` 파일을 수정하여 이루어집니다.

- **주요 보안 설정**:
    - **루트 로그인 금지**: `root` 계정으로 직접 `ssh` 접속을 허용하는 것은 매우 위험합니다. 일반 계정으로 접속한 뒤 `sudo`를 사용하는 것이 훨씬 안전합니다.
      `PermitRootLogin no`

    - **비밀번호 인증 대신 공개키(Public Key) 인증 사용**: 비밀번호는 무차별 대입 공격(Brute-force attack)에 취약할 수 있습니다. 훨씬 더 안전한 공개키 기반 인증만 사용하도록 강제하는 것이 좋습니다.
      `PasswordAuthentication no`
      `PubkeyAuthentication yes`

    - **특정 사용자/그룹만 접속 허용**: `AllowUsers` 또는 `AllowGroups` 지시어를 사용하여 `ssh` 접속이 허용된 사용자를 명시적으로 지정합니다.
      `AllowUsers user1 user2`
      `AllowGroups ssh-users`

    - **기본 포트 변경**: `ssh`의 기본 포트인 22번은 자동화된 스캔 공격의 주된 대상이 됩니다. 1024 이상의 비표준 포트(예: `2222`)로 변경하면 이러한 공격을 상당수 피할 수 있습니다.
      `Port 2222`

- **설정 적용**: `/etc/ssh/sshd_config` 파일을 수정한 후에는 `sshd` 서비스를 재시작해야 합니다.
  `sudo systemctl restart sshd`

## 4. MFA (Multi-Factor Authentication) / 2FA (2-Factor Authentication)

- **개념**: `ssh` 로그인 시, 비밀번호나 공개키 외에 추가적인 인증 요소(Factor)를 요구하여 보안을 한층 더 강화하는 방식입니다. 일반적으로 스마트폰의 인증 앱(Google Authenticator, Authy 등)이 생성하는 일회용 비밀번호(OTP)를 두 번째 인증 요소로 사용합니다.

- **구현**: `google-authenticator-libpam`과 같은 PAM(Pluggable Authentication Modules) 모듈을 설치하고, `/etc/pam.d/sshd`와 `/etc/ssh/sshd_config` 파일을 수정하여 `ssh` 인증 과정에 OTP 확인 절차를 추가할 수 있습니다.

이러한 접근 제어 전략들을 계층적으로 적용함으로써, 시스템에 대한 비인가 접근을 효과적으로 차단하고 내부 사용자의 권한을 적절히 통제하여 서버의 전반적인 보안 수준을 크게 향상시킬 수 있습니다.
