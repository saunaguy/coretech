# 3-1-7: 백업/복구: `rsync`/`tar`, 보관주기/오프사이트, RPO/RTO

아무리 시스템을 안정적으로 운영하더라도 하드웨어 고장, 소프트웨어 버그, 사용자 실수, 랜섬웨어 공격 등 데이터 유실의 위험은 항상 존재합니다. 따라서 체계적인 백업 및 복구 전략을 수립하고 정기적으로 테스트하는 것은 서버 운영의 가장 중요한 책임 중 하나입니다.

## 1. 백업 도구: `rsync`와 `tar`

- **`rsync` (Remote Sync)**: 원격 또는 로컬 디렉터리 간의 데이터를 효율적으로 동기화하는 데 최적화된 도구입니다. (자세한 사용법은 `2-4-8` 참고)
    - **증분 백업(Incremental Backup)**: `rsync`는 변경된 파일이나 파일의 변경된 부분만 전송하므로, 반복적인 백업 작업에 매우 효율적입니다. 매일 변경되는 데이터를 백업하는 데 가장 널리 사용됩니다.
    - **사용 예시 (원격 백업 서버로 데이터 동기화)**:
      ```bash
      # /var/www/html 디렉터리의 내용을 backup-server의 /backup/web/ 디렉터리로 동기화
      # --delete 옵션으로 원본에서 삭제된 파일은 백업에서도 삭제
      rsync -avz --delete /var/www/html/ user@backup-server:/backup/web/
      ```

- **`tar`**: 여러 파일과 디렉터리를 하나의 아카이브 파일(`.tar`)로 묶는 도구입니다. (자세한 사용법은 `2-4-2` 참고)
    - **풀 백업(Full Backup)**: 특정 시점의 데이터 전체를 하나의 파일로 묶어 보관하는 데 유용합니다. 주로 매주 또는 매월 단위의 전체 백업에 사용됩니다.
    - **사용 예시 (데이터베이스 덤프 파일과 설정 파일을 함께 묶기)**:
      ```bash
      # DB 덤프 생성
      mysqldump -u root -p my_db > my_db.sql

      # 덤프 파일과 Nginx 설정 디렉터리를 날짜별로 압축하여 백업
      tar -zcvf web_backup_$(date +%Y%m%d).tar.gz my_db.sql /etc/nginx/
      ```

## 2. 백업 전략의 핵심 요소

### 보관 주기 (Retention Policy)
- **개념**: 백업 데이터를 얼마나 오랫동안 보관할지를 결정하는 정책입니다. 모든 백업을 영원히 보관할 수는 없으므로, 비즈니스 요구사항과 법적 규제에 따라 합리적인 주기를 설정해야 합니다.
- **GFS (Grandfather-Father-Son) 전략**: 가장 널리 사용되는 보관 주기 전략 중 하나입니다.
    - **Son (아들)**: 매일 수행하는 증분/차등 백업 (일일 백업). 보통 1~2주간 보관합니다.
    - **Father (아버지)**: 매주 수행하는 전체 백업 (주간 백업). 보통 1~3개월간 보관합니다.
    - **Grandfather (할아버지)**: 매월 또는 매 분기 수행하는 전체 백업 (월간/분기 백업). 1년 이상 장기 보관합니다.

### 오프사이트(Off-site) 및 오프라인(Offline) 백업
- **오프사이트 백업**: 물리적으로 다른 위치(다른 데이터 센터, 클라우드 스토리지 등)에 백업 데이터를 보관하는 것입니다. 이는 화재, 지진 등 데이터 센터 전체에 영향을 미치는 재난 상황으로부터 데이터를 보호하기 위해 필수적입니다.
- **오프라인 백업 (에어 갭, Air-gapped)**: 백업 데이터가 저장된 매체(테이프, 외장 하드 등)를 네트워크에서 완전히 분리하여 보관하는 것입니다. 이는 랜섬웨어 공격으로부터 백업 데이터 자체를 보호하는 가장 확실한 방법입니다. 공격자는 네트워크로 연결되지 않은 백업을 암호화할 수 없습니다.

## 3. 복구 목표: RPO와 RTO

백업 전략은 단순히 데이터를 복사하는 것에서 그치지 않고, 장애 발생 시 비즈니스를 얼마나 빨리, 어느 시점으로 복구할 것인지에 대한 목표를 설정하는 것에서 시작됩니다.

### RPO (Recovery Point Objective, 복구 목표 시점)
- **개념**: 장애가 발생했을 때, **어느 시점의 데이터로 복구할 것인지**를 나타내는 목표입니다. 즉, 비즈니스가 감당할 수 있는 **최대 데이터 손실량**을 의미합니다.
- **예시**:
    - RPO가 24시간이라면, 최소한 하루에 한 번은 백업이 이루어져야 합니다. 최악의 경우 약 24시간 분량의 데이터가 손실될 수 있습니다.
    - RPO가 15분이라면, 15분마다 데이터베이스 트랜잭션 로그를 백업하는 등의 더 적극적인 백업 전략이 필요합니다.

### RTO (Recovery Time Objective, 복구 목표 시간)
- **개념**: 장애가 발생한 시점부터 서비스가 다시 정상적으로 동작하기까지 걸리는 **최대 허용 시간**을 의미합니다.
- **예시**:
    - RTO가 4시간이라면, 장애 인지, 원인 분석, 데이터 복구, 서비스 재개까지의 모든 과정이 4시간 안에 완료되어야 합니다.
    - RTO를 단축하기 위해서는 자동화된 복구 스크립트, 고가용성(HA) 솔루션, 빠른 스토리지 등이 필요하며, 이는 더 많은 비용을 의미합니다.

**RPO와 RTO는 비즈니스의 중요도에 따라 결정되며, 이 두 가지 목표가 백업 주기, 백업 방법, 백업 인프라 등 전체 백업 및 복구 전략의 방향을 결정합니다.** 예를 들어, 금융 거래 시스템은 RPO와 RTO가 거의 0에 가까워야 하므로 매우 비싼 실시간 복제 솔루션이 필요하지만, 사내 블로그는 RPO/RTO가 24시간 이상이어도 무방할 수 있습니다.

마지막으로, **백업은 정기적인 복구 테스트를 거치지 않으면 없는 것과 같습니다.** 실제 상황처럼 복구 절차를 주기적으로 점검하고 훈련해야만, 진짜 위기 상황에서 당황하지 않고 신속하게 서비스를 복구할 수 있습니다.
