# 3-1-3: 로깅 운영: journal 보존/로테이션, `rsyslog`, 구조화 로그

서버 운영에서 로그는 장애의 원인을 찾고, 보안 사고를 추적하며, 시스템의 상태를 분석하는 가장 기본적인 데이터입니다. 따라서 로그를 어떻게 효과적으로 수집, 보존, 관리할 것인지에 대한 전략은 매우 중요합니다.

## 1. `systemd-journald` 로그 보존 및 관리

`systemd-journald`는 기본적으로 로그를 `/run/log/journal/` 디렉터리에 저장합니다. 이 디렉터리는 `tmpfs`에 마운트되어 있어, 시스템을 재부팅하면 모든 로그가 사라집니다. 서버 운영 환경에서는 과거의 로그를 분석해야 하므로, 로그를 영구적으로 보존하도록 설정을 변경해야 합니다.

### 영구 로그 저장 설정

- **방법**: `/etc/systemd/journald.conf` 파일을 수정하여 `Storage` 옵션을 `persistent`로 변경하거나, 단순히 `/var/log/journal` 디렉터리를 생성해주면 됩니다.

  ```bash
  # /var/log/journal 디렉터리 생성 (가장 간단한 방법)
  sudo mkdir -p /var/log/journal
  # systemd-journald 재시작
  sudo systemctl restart systemd-journald
  ```
  - 이제부터 로그는 `/var/log/journal/` 디렉터리에 영구적으로 저장됩니다.

### 로그 로테이션(Rotation) 및 크기 제한

로그가 무한정 쌓이면 디스크 공간을 모두 차지하게 되므로, `journald`는 자동으로 오래된 로그를 삭제(로테이션)하는 기능을 내장하고 있습니다. `/etc/systemd/journald.conf` 파일에서 관련 옵션을 조정할 수 있습니다.

- **주요 옵션**:
    - `SystemMaxUse=`: `journald`가 디스크에서 차지할 수 있는 최대 공간 (예: `4G`).
    - `SystemKeepFree=`: `journald`가 로그를 저장하는 파일 시스템에 항상 남겨두어야 할 최소 여유 공간 (예: `1G`).
    - `MaxFileSec=`: 로그 파일을 얼마나 오랫동안 보관할지 시간으로 지정 (예: `1month`).

## 2. `rsyslog`를 이용한 중앙 집중식 로깅

여러 대의 서버를 운영할 경우, 각 서버에 개별적으로 접속하여 로그를 확인하는 것은 매우 비효율적입니다. `rsyslog`는 네트워크를 통해 여러 서버의 로그를 하나의 **중앙 로그 서버**로 전송하는 강력한 기능을 제공합니다.

- **동작 방식**:
    1.  **클라이언트 서버**: `rsyslog` 설정을 통해 자신의 로그를 중앙 로그 서버의 특정 포트(보통 UDP 514)로 전달합니다.
    2.  **중앙 로그 서버**: 다른 서버들로부터 로그를 수신하여, 호스트 이름이나 서비스별로 분류하여 파일에 저장합니다.

- **클라이언트 설정 예시 (`/etc/rsyslog.conf`)**:
  ```
  # 모든 로그(*.*)를 UDP를 통해 logserver.example.com으로 전송
  *.* @logserver.example.com:514
  
  # TCP를 통해 안정적으로 전송하려면 @@ 사용
  # *.* @@logserver.example.com:514
  ```

- **장점**:
    - **관리 효율성**: 모든 로그를 한 곳에서 검색하고 분석할 수 있습니다.
    - **보안**: 공격자가 서버에 침투하여 로컬 로그를 삭제하더라도, 중앙 로그 서버에는 원본 로그가 남아있어 추적이 가능합니다.

## 3. 구조화 로그 (Structured Logging)

전통적인 로그는 사람이 읽기 쉬운 자유로운 형태의 텍스트 문자열이었습니다.
`INFO: User 'admin' logged in from 192.168.1.100`

**구조화 로그**는 로그 메시지를 `key-value` 형태, 주로 **JSON** 형식으로 기록하는 현대적인 로깅 방식입니다.
`{"timestamp": "2025-09-25T10:00:00Z", "level": "INFO", "event": "user_login", "user": "admin", "source_ip": "192.168.1.100"}`

- **장점**:
    - **기계 가독성(Machine-Readable)**: 로그를 파싱(parsing)하기 매우 쉬워집니다. `grep`이나 정규 표현식으로 복잡하게 처리할 필요 없이, 특정 `key`의 `value`를 기준으로 쉽게 필터링하고 검색할 수 있습니다.
    - **강력한 분석**: Elasticsearch, Splunk, Datadog과 같은 로그 분석 플랫폼과 완벽하게 연동하여, 특정 이벤트의 발생 빈도, 평균 응답 시간 등 다양한 지표를 시각화하고 분석하는 데 매우 유리합니다.

- **`systemd-journald`와 구조화 로그**: `journald`는 이미 구조화된 방식으로 로그를 저장하고 있습니다. `journalctl -o json-pretty` 명령을 사용하면 로그를 JSON 형식으로 출력할 수 있어, 다른 분석 시스템으로 전달하기 용이합니다.

  ```bash
  journalctl -n 1 -o json-pretty
  ```

### 로깅 운영 전략 요약

1.  **영구 보존**: `systemd-journald`의 로그를 영구적으로 저장하도록 설정하고, 시스템의 디스크 용량에 맞게 로테이션 정책을 수립한다.
2.  **중앙화**: 여러 대의 서버를 운영한다면, `rsyslog` 등을 이용하여 로그를 중앙 로그 서버로 집계하여 관리 효율과 보안을 높인다.
3.  **구조화**: 새로 개발하는 애플리케이션은 가급적 JSON과 같은 구조화된 형식으로 로그를 남기도록 구현하여, 로그의 검색, 분석, 시각화가 용이하도록 만든다.
