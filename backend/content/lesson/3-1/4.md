# 3-1-4: 성능/자원 운영: `ulimit`, `cgroups` v2, OOM 대응

안정적인 서비스를 위해서는 애플리케이션이 사용할 수 있는 시스템 자원(CPU, 메모리, 파일 핸들 등)을 적절히 제한하고 모니터링하며, 예기치 않은 상황에 대비하는 것이 중요합니다. 이는 특정 서비스의 버그나 과부하가 전체 시스템의 안정성을 해치는 것을 방지합니다.

## 1. `ulimit`: 프로세스 자원 한도 설정

(이 내용은 `2-3-8`에서 다루었지만, 운영 관점에서 다시 한번 정리합니다.)

`ulimit`은 특정 사용자나 셸 세션에서 실행되는 프로세스가 사용할 수 있는 자원의 **소프트(soft) 한도**와 **하드(hard) 한도**를 설정합니다. 특히 웹 서버나 데이터베이스와 같이 많은 동시 연결을 처리해야 하는 서비스의 경우, **열린 파일 디스크립터(open files)**의 한도가 낮게 설정되어 있으면 "Too many open files" 에러와 함께 서비스가 실패할 수 있습니다.

- **운영 시나리오**: `nginx` 서비스가 많은 동시 접속을 처리할 수 있도록 파일 디스크립터 한도를 높여야 한다.

- **해결 방법 (`systemd` Drop-in 사용)**:
  패키지로 설치된 `nginx.service`의 설정을 `systemctl edit nginx.service`를 통해 재정의합니다. `[Service]` 섹션에 `LimitNOFILE` 지시어를 추가합니다.

  - `/etc/systemd/system/nginx.service.d/override.conf`:
    ```ini
    [Service]
    # 소프트 한도와 하드 한도를 모두 65536으로 설정
    LimitNOFILE=65536
    ```
  - `LimitNOFILE`은 `ulimit -n`에 해당합니다. 이 외에도 `LimitNPROC`(프로세스 수), `LimitCORE`(코어 덤프 크기) 등 다양한 `Limit...` 지시어가 있습니다.

## 2. `cgroups` v2: 서비스 단위 자원 통제의 표준

`cgroups`(Control Groups)는 특정 프로세스 그룹(예: 특정 `systemd` 서비스)의 자원 사용량을 정교하게 제어하는 커널 기능입니다. `cgroups` v1에 비해 v2는 계층 구조가 단순화되고 자원 제어 방식이 더 일관성 있게 개선되었습니다.

`systemd`는 `cgroups` v2를 적극적으로 활용하여 서비스별 자원 관리를 매우 쉽게 만들어 줍니다. `systemd` 유닛 파일의 `[Service]` 섹션에 관련 지시어를 추가하기만 하면 됩니다.

- **주요 자원 제어 지시어**:
    - **CPU 제어**:
        - `CPUWeight=`: 다른 서비스와 CPU 시간을 경쟁할 때의 가중치. (기본 100, 높을수록 더 많은 CPU 시간 할당)
        - `CPUQuota=`: CPU 사용률의 절대적인 상한선을 설정. (예: `200%` -> CPU 2개 코어만큼만 사용)
    - **메모리 제어**:
        - `MemoryHigh=`: 메모리 사용량이 이 값에 도달하면 커널이 메모리 회수를 시작 (소프트 한도).
        - `MemoryMax=`: 메모리 사용량의 절대적인 상한선. 이 값을 초과하면 OOM Killer가 동작할 수 있습니다.
        - `MemorySwapMax=`: 스왑 메모리 사용량의 상한선.
    - **I/O 제어**:
        - `IOWeight=`: 블록 I/O 대역폭 경쟁 시의 가중치.
        - `IOReadBandwidthMax=`, `IOWriteBandwidthMax=`: 특정 장치에 대한 읽기/쓰기 대역폭의 상한선.

- **운영 시나리오**: `my-analytics.service`가 시스템의 CPU를 과도하게 사용하여 다른 중요한 서비스(예: 웹 서버)의 응답이 느려지는 것을 방지하고 싶다.

- **해결 방법 (`systemd` Drop-in 사용)**:
  ```ini
  # /etc/systemd/system/my-analytics.service.d/resource-control.conf
  [Service]
  # 이 서비스는 CPU 자원의 50%까지만 사용하도록 제한
  CPUQuota=50%
  # 메모리도 4G까지만 사용하도록 제한
  MemoryMax=4G
  ```

## 3. OOM (Out-of-Memory) Killer 대응

OOM Killer는 시스템을 보호하기 위한 최후의 수단이지만, 어떤 프로세스가 종료될지 예측하기 어렵다는 문제가 있습니다. 특히 `MariaDB`나 `Redis`와 같은 중요한 데이터베이스 서비스가 종료되면 심각한 장애로 이어질 수 있습니다.

- **`OOMScoreAdjust`**: `systemd` 유닛 파일에서 이 값을 설정하여 OOM Killer가 특정 프로세스를 종료할 우선순위를 조정할 수 있습니다.
    - 값의 범위는 -1000 (종료되지 않음) 부터 1000 (가장 먼저 종료됨) 까지입니다.

- **운영 시나리오**: 어떤 경우에도 `mariadb.service`는 OOM Killer에 의해 종료되지 않도록 보호하고 싶다.

- **해결 방법 (`systemd` Drop-in 사용)**:
  ```ini
  # /etc/systemd/system/mariadb.service.d/oom-protection.conf
  [Service]
  # OOM Killer의 종료 대상에서 사실상 제외시킴
  OOMScoreAdjust=-1000
  ```
  - **주의**: 중요한 서비스를 보호하는 것은 좋지만, 너무 많은 서비스를 이런 식으로 보호하면 정작 메모리가 부족할 때 OOM Killer가 종료할 프로세스를 찾지 못해 시스템 전체가 멈출 수 있습니다. 반드시 신중하게, 최소한의 핵심 서비스에만 적용해야 합니다.

이처럼 `systemd`가 제공하는 자원 관리 기능들을 활용하면, 멀티테넌트 환경이나 다양한 서비스가 공존하는 복잡한 서버에서도 각 서비스의 영향을 격리하고 시스템 전체의 안정성과 예측 가능성을 크게 높일 수 있습니다.
