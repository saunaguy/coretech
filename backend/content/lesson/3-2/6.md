# 3-2-6: SELinux/PAM: AVC 해석, 인증 실패 추적

파일 권한(rwx)이 올바르고 방화벽도 열려 있는데 서비스가 제대로 동작하지 않는다면, 보이지 않는 보안 계층인 **SELinux**나 **PAM**이 원인일 수 있습니다. 이들은 리눅스의 보안을 한층 더 강화하지만, 그만큼 트러블슈팅을 더 복잡하게 만들기도 합니다.

## 1. SELinux (Security-Enhanced Linux) 트러블슈팅

- **개념**: SELinux는 전통적인 DAC(Discretionary Access Control - 소유자 기반 권한)를 넘어, 시스템의 모든 프로세스와 파일에 **보안 컨텍스트(Security Context)**라는 라벨을 붙이고, 미리 정의된 정책(Policy)에 따라 이들 간의 상호작용을 강제로 제어하는 **MAC(Mandatory Access Control)** 시스템입니다.
- **시나리오**: `nginx`가 `/srv/www` 디렉터리의 파일을 읽도록 설정했는데, "Permission Denied" 에러가 발생합니다. `ls -l`로 확인한 파일 권한은 분명히 `nginx` 사용자가 읽을 수 있도록 되어 있습니다.

### SELinux 상태 확인

- **`getenforce`**: 현재 SELinux 모드를 확인합니다.
    - `Enforcing`: 정책에 위반되는 모든 접근을 차단하고 로그를 남깁니다. (보안)
    - `Permissive`: 위반 행위를 차단하지는 않고, 로그만 남깁니다. (디버깅용)
    - `Disabled`: SELinux가 비활성화되어 있습니다.

- **임시로 Permissive 모드로 전환**: 문제가 SELinux 때문인지 빠르게 확인하려면, 잠시 `Permissive` 모드로 변경해 볼 수 있습니다.
  ```bash
  sudo setenforce 0  # Permissive 모드로 전환
  # ... 서비스 동작 테스트 ...
  sudo setenforce 1  # 다시 Enforcing 모드로 복귀
  ```
  만약 `Permissive` 모드에서 서비스가 정상 동작한다면, 원인은 100% SELinux입니다.

### AVC (Access Vector Cache) 로그 해석

SELinux가 어떤 접근을 차단하면, 그 기록을 `/var/log/audit/audit.log`에 **AVC 거부(denial)** 로그로 남깁니다. 이 로그를 해석하는 것이 문제 해결의 핵심입니다.

- **`ausearch`**: `audit.log`에서 AVC 로그를 검색합니다.
  ```bash
  sudo ausearch -m avc -ts recent
  ```

- **`sealert` (권장)**: `setroubleshoot-server` 패키지를 설치하면, `sealert` 도구가 AVC 로그를 사람이 이해하기 쉬운 형태로 분석하고 **해결책까지 제시**해 줍니다.
  ```bash
  sudo sealert -a /var/log/audit/audit.log
  ```
  - `sealert`의 출력은 `nginx` 프로세스(`httpd_t` 컨텍스트)가 `httpd_sys_content_t` 라벨이 붙은 파일만 읽을 수 있는데, 접근하려는 `/srv/www` 디렉터리의 파일은 `default_t` 컨텍스트를 가지고 있어 접근이 거부되었다고 알려줄 것입니다.

### 보안 컨텍스트(Label) 관리

- **`ls -Z`**: 파일과 디렉터리의 SELinux 보안 컨텍스트를 확인합니다.
  `ls -lZ /srv/www`

- **`chcon` (Change Context)**: 파일의 보안 컨텍스트를 **일시적으로** 변경합니다. 시스템 재시작이나 파일 시스템 재라벨링 시 원래대로 돌아갈 수 있습니다.
  ```bash
  # /srv/www 디렉터리와 그 하위 파일들의 타입을 httpd_sys_content_t로 변경
  sudo chcon -R -t httpd_sys_content_t /srv/www
  ```

- **`semanage fcontext` & `restorecon` (권장)**: 파일 시스템 경로에 대한 기본 컨텍스트 정책을 영구적으로 추가하고 적용하는 올바른 방법입니다.
  ```bash
  # 1. /srv/www와 그 하위 모든 파일/디렉터리는 httpd_sys_content_t 컨텍스트를 갖는다는 정책 추가
  sudo semanage fcontext -a -t httpd_sys_content_t "/srv/www(/.*)?"

  # 2. 위에서 정의한 정책을 실제 파일 시스템에 적용
  sudo restorecon -R -v /srv/www
  ```

## 2. PAM (Pluggable Authentication Modules) 트러블슈팅

- **개념**: PAM은 `login`, `sshd`, `sudo` 등 인증이 필요한 다양한 서비스에 대해, 사용자 인증 방식을 유연하게 설정하고 관리할 수 있게 해주는 프레임워크입니다. `/etc/pam.d/` 디렉터리 아래에 각 서비스별 설정 파일이 위치합니다.
- **시나리오**: 특정 사용자가 `ssh`나 콘솔로 로그인이 계속 실패하는데, 비밀번호는 분명히 올바릅니다.

### 인증 실패 추적

- **로그 파일 확인**: PAM 관련 인증 실패는 주로 `/var/log/secure` (RHEL 계열) 또는 `/var/log/auth.log` (Debian 계열) 파일에 기록됩니다.
  ```bash
  sudo tail -f /var/log/secure
  ```
  - 로그를 실시간으로 확인하면서 로그인을 시도해 보면, 어떤 PAM 모듈에서 인증이 실패했는지에 대한 단서를 얻을 수 있습니다. (예: `pam_access`, `pam_time` 등)

- **`/etc/pam.d/` 설정 파일 검토**: 해당 서비스의 PAM 설정 파일(예: `/etc/pam.d/sshd`)을 열어 어떤 모듈들이 사용되는지 확인합니다.
  - `account required pam_access.so`: `/etc/security/access.conf` 파일에 정의된 규칙에 따라 로그인을 제어하는 모듈. 이 파일에 해당 사용자가 허용되어 있는지 확인해야 합니다.
  - `account required pam_nologin.so`: `/etc/nologin` 파일이 존재하면 `root`를 제외한 모든 사용자의 로그인을 막는 모듈.

- **`pam_tally2`**: 로그인 실패 횟수를 기록하고, 일정 횟수 이상 실패 시 계정을 잠그는 `pam_tally2` 모듈이 원인일 수 있습니다.
  ```bash
  # user01 사용자의 로그인 실패 횟수 확인
  sudo pam_tally2 --user user01

  # user01 사용자의 실패 카운트 리셋
  sudo pam_tally2 --user user01 --reset
  ```

SELinux와 PAM은 복잡하지만, 리눅스 시스템 보안의 핵심적인 부분입니다. 문제가 발생했을 때 관련 로그(`audit.log`, `secure`/`auth.log`)를 확인하고, `sealert`, `chcon`, `pam_tally2`와 같은 전용 도구를 사용하여 해결하는 체계적인 접근이 중요합니다.
