# 3-2-2: 서비스 장애: `systemctl`/`journalctl`, StartLimit/Restart loop

서버는 실행 중이지만 특정 서비스(예: 웹 서버, 데이터베이스)가 동작하지 않는 경우는 매우 흔한 장애 상황입니다. `systemd` 환경에서 서비스 장애의 원인을 찾고 해결하는 체계적인 접근 방법을 알아봅니다.

## 1. 1단계: 상태 확인 (`systemctl status`)

서비스 장애 발생 시 가장 먼저 해야 할 일은 `systemctl status` 명령으로 서비스의 현재 상태를 확인하는 것입니다. 이 명령어는 서비스의 활성화 여부, PID, 메모리 사용량, 그리고 가장 중요한 **최근 로그 몇 줄**을 보여주어 문제의 단서를 제공합니다.

```bash
# nginx 서비스의 상태 확인
sudo systemctl status nginx.service
```

- **주요 상태 정보**:
    - `Active: active (running)`: 정상 실행 중. (하지만 서비스가 논리적으로는 오동작하고 있을 수 있음)
    - `Active: inactive (dead)`: 정상적으로 중지된 상태.
    - `Active: failed (Result: ...)`: 시작에 실패했음. `Result` 부분에 실패 원인(예: `exit-code`, `signal`)이 표시됩니다. **이것이 가장 중요한 단서입니다.**
    - `Loaded: ...; disabled; ...`: 서비스가 활성화(`enable`)되지 않아 부팅 시 시작되지 않았을 수 있습니다.
    - `Loaded: not-found; ...`: 유닛 파일 자체를 찾을 수 없는 경우.

- **실패 예시 분석**:
  ```
  ● nginx.service - A high performance web server
     Loaded: loaded (/lib/systemd/system/nginx.service; enabled; vendor preset: enabled)
     Active: failed (Result: exit-code) since Thu 2025-09-25 10:00:00 KST; 5s ago
    Process: 1234 ExecStart=/usr/sbin/nginx -g "daemon on; master_process on;" (code=exited, status=1/FAILURE)

Sep 25 10:00:00 server1 systemd[1]: Starting A high performance web server...
Sep 25 10:00:00 server1 nginx[1234]: nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)
Sep 25 10:00:00 server1 systemd[1]: nginx.service: Control process exited, code=exited, status=1/FAILURE
Sep 25 10:00:00 server1 systemd[1]: nginx.service: Failed with result 'exit-code'.
Sep 25 10:00:00 server1 systemd[1]: Failed to start A high performance web server.
  ```
  - 위 로그에서 `nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)` 라는 결정적인 에러 메시지를 통해, **80번 포트를 다른 프로세스가 이미 사용하고 있어 `nginx`가 시작하지 못했음**을 알 수 있습니다.

## 2. 2단계: 상세 로그 분석 (`journalctl`)

`systemctl status`가 보여주는 최근 로그만으로 원인을 파악하기 어렵다면, `journalctl`을 사용하여 해당 서비스의 전체 로그를 시간순으로 상세하게 분석해야 합니다.

- **주요 명령어**:
  ```bash
  # 해당 서비스의 모든 로그를 시간 역순(최신 로그가 위로)으로 보기
  journalctl -u nginx.service -r

  # 부팅 이후의 모든 로그를 따라가며 실시간으로 보기 (-f)
  journalctl -u nginx.service -f

  # 특정 시간 이후의 로그만 필터링
  journalctl -u nginx.service --since "10 minutes ago"
  ```

- **분석 팁**:
    - 로그의 가장 마지막 부분부터 거슬러 올라가며 `error`, `failed`, `fatal` 등의 키워드를 찾아봅니다.
    - 에러 메시지가 발생한 시점 바로 이전의 로그들을 살펴보면, 에러의 원인이 되는 단서를 찾을 수 있는 경우가 많습니다. (예: 설정 파일을 읽는 로그 바로 다음에 파싱 에러가 발생)

## 3. 무한 재시작 루프 (Start-Limit / Restart Loop) 해결

서비스 유닛 파일에 `Restart=always` 또는 `Restart=on-failure`가 설정되어 있을 때, 서비스가 시작하자마자 계속해서 실패하면 `systemd`는 서비스를 계속해서 재시작하려고 시도합니다. 이는 짧은 시간 동안 수많은 실패 로그를 남기고 시스템에 부하를 줍니다.

`systemd`는 이러한 무한 재시작 루프를 방지하기 위해 **Start-Limit** 메커니즘을 가지고 있습니다.

- **`StartLimitIntervalSec=`** (기본값 10초): 이 시간 동안
- **`StartLimitBurst=`** (기본값 5번): 이 횟수 이상으로 서비스 시작이 실패하면, `systemd`는 해당 서비스 재시작을 포기하고 `failed` 상태로 전환합니다.

- **장애 상황**: `systemctl status` 확인 시, `start-limit-hit` 라는 메시지와 함께 서비스가 `failed` 상태로 되어 있습니다.
  ```
  nginx.service: Start request repeated too quickly.
  nginx.service: Failed with result 'exit-code'.
  Failed to start A high performance web server.
  nginx.service: Triggering OnFailure= dependencies.
  ```

- **해결 절차**:
    1.  **원인 분석**: `journalctl -u <service_name>`을 통해 서비스가 왜 계속해서 실패하는지에 대한 근본 원인을 찾습니다. (설정 파일 오류, 권한 문제, 포트 충돌 등)
    2.  **문제 해결**: 찾은 원인을 해결합니다. (예: 설정 파일 문법 수정, 파일 권한 변경, 충돌하는 프로세스 종료 등)
    3.  **Start-Limit 카운터 리셋**: 문제를 해결했더라도, `systemd`는 아직 해당 서비스를 "실패한 서비스"로 기억하고 있을 수 있습니다. `systemctl reset-failed` 명령으로 이 상태를 초기화해 주어야 합니다.
        ```bash
        sudo systemctl reset-failed nginx.service
        ```
    4.  **서비스 재시작**: 이제 다시 서비스를 시작합니다.
        ```bash
        sudo systemctl start nginx.service
        ```

서비스 장애 트러블슈팅은 **`상태 확인 -> 상세 로그 분석 -> 원인 해결 -> 재시작`** 이라는 체계적인 절차를 따르는 것이 중요합니다. 특히 `systemctl status`와 `journalctl`이 보여주는 로그 메시지를 꼼꼼히 읽는 것이 문제 해결의 가장 빠른 지름길입니다.
