# 3-2-4: 파일/디스크 이슈: `lsof`/`fuser`, orphan inode, 로테이션 후 핸들

디스크 공간이 충분한데 파일이 생성되지 않거나, 특정 파일이나 디스크를 사용 중인 프로세스를 찾아야 하는 등 파일 및 디스크 관련 문제는 다양하게 발생합니다. 여기서는 이러한 문제들을 해결하는 데 사용되는 고급 도구와 개념을 알아봅니다.

## 1. `lsof`와 `fuser`: "이 파일을 누가 쓰고 있지?"

- **시나리오**: 특정 파일 시스템을 `umount`하려고 할 때 "target is busy"라는 메시지와 함께 실패하는 경우, 또는 특정 로그 파일을 어떤 프로세스가 계속 사용하고 있는지 확인하고 싶을 때.

### `lsof` (List Open Files)
- **기능**: 시스템에서 열려 있는 모든 파일과, 그 파일을 사용하고 있는 프로세스의 목록을 보여주는 매우 강력한 도구입니다. 리눅스에서는 일반 파일뿐만 아니라 디렉터리, 라이브러리, 네트워크 소켓 등 모든 것이 파일로 취급되므로 활용 범위가 매우 넓습니다.

- **주요 사용법**:
  ```bash
  # /var/log/messages 파일을 열고 있는 모든 프로세스 확인
  sudo lsof /var/log/messages

  # 특정 사용자(예: nginx)가 열고 있는 모든 파일 확인
  sudo lsof -u nginx

  # 특정 프로세스(PID 1234)가 열고 있는 모든 파일 확인
  sudo lsof -p 1234

  # 특정 포트(예: 80)를 사용하고 있는 프로세스 확인
  sudo lsof -i :80

  # 특정 디렉터리(/data) 하위의 파일을 열고 있는 모든 프로세스 확인
  # +D 옵션은 재귀적으로 보여줌
  sudo lsof +D /data
  ```

### `fuser` (File User)
- **기능**: `lsof`보다 간단하게, 특정 파일이나 파일 시스템을 사용하고 있는 프로세스의 PID를 찾아주는 데 특화된 도구입니다.

- **주요 사용법**:
  ```bash
  # /data 디렉터리(파일 시스템)를 사용 중인 프로세스 확인
  fuser -v /data

  # /data 디렉터리를 사용 중인 프로세스에 시그널 보내기
  # -k 옵션은 SIGKILL 시그널을 보냄
  sudo fuser -k /data
  ```

## 2. 디스크 공간 문제 심화

### Orphan Inode (고아 아이노드)
- **시나리오**: `df`로는 디스크가 꽉 찼다고 나오는데, `du`로 모든 디렉터리의 용량을 합산해 봐도 `df`의 사용량에 한참 미치지 못하는 경우.
- **원인**: 어떤 프로세스가 파일을 열어 사용하고 있는 상태에서, 다른 프로세스가 해당 파일의 디렉터리 엔트리(이름)를 삭제한 경우입니다. 파일의 이름은 사라졌지만, 파일을 사용 중인 프로세스가 존재하는 한 커널은 파일의 데이터(아이노드와 데이터 블록)를 디스크에서 삭제하지 않습니다. 이 상태의 파일을 **Orphan Inode (고아 아이노드)** 또는 "deleted but still open" 상태라고 합니다.
- **해결 방법**:
  1.  `lsof`를 사용하여 삭제된 파일을 찾습니다.
      ```bash
      # lsof의 결과 중 "(deleted)"라고 표시된 파일을 찾음
      sudo lsof | grep "(deleted)"
      ```
  2.  해당 파일을 열고 있는 프로세스를 확인하고, 안전하게 재시작하거나 종료합니다. 프로세스가 종료되면 커널은 비로소 해당 파일이 차지하던 디스크 공간을 해제합니다.

### 로그 로테이션 후 핸들(Handle) 문제
- **시나리오**: 로그 파일(`access.log`)의 크기가 너무 커져서, `mv access.log access.log.old`로 백업하고 `touch access.log`로 새 파일을 만들었습니다. 그런데 웹 서버는 여전히 예전 파일인 `access.log.old`에 로그를 계속 기록하고, 새로 만든 `access.log`에는 아무것도 기록되지 않습니다.
- **원인**: 웹 서버 프로세스는 처음에 `access.log`를 열 때 파일 이름이 아닌 파일의 **아이노드(inode)**를 가리키는 파일 핸들(File Handle)을 얻습니다. `mv` 명령은 파일의 내용은 그대로 둔 채 이름만 바꾸므로, 프로세스가 잡고 있는 핸들은 여전히 `access.log.old`로 이름이 바뀐 원본 파일을 가리키고 있습니다.
- **해결 방법**:
    - **프로세스 재시작**: 가장 확실한 방법은 로그를 기록하는 서비스(웹 서버 등)를 재시작하는 것입니다. 재시작하면서 새로운 `access.log` 파일의 핸들을 얻게 됩니다.
    - **`copytruncate`**: `logrotate` 도구의 옵션 중 하나로, 로그 파일을 이동(`mv`)하는 대신, 원본 로그 파일의 내용을 복사한 뒤 원본 파일의 내용을 비우는 방식입니다. 이 방식은 프로세스가 잡고 있는 파일 핸들이 그대로 유지되므로 서비스 재시작 없이 안전하게 로그를 로테이션할 수 있습니다.

이처럼 파일과 디스크 관련 문제는 단순히 용량 확인을 넘어, 프로세스와 파일 시스템의 내부 동작 원리를 이해해야 해결할 수 있는 경우가 많습니다. `lsof`는 이러한 문제 해결에 있어 가장 중요한 도구 중 하나이므로 사용법을 잘 익혀두는 것이 좋습니다.
