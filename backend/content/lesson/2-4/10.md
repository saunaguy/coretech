# 2-4-10: 부팅/서비스 트러블슈팅 (systemd 유닛 작성과 디버깅)

`systemd`는 현대 리눅스 시스템의 핵심으로, 부팅 프로세스를 관리하고 시스템 서비스를 제어합니다. 따라서 `systemd`의 동작 방식을 이해하고 유닛(Unit) 파일을 작성하며 문제를 해결하는 능력은 시스템 관리자에게 필수적입니다.

## 1. `systemd` 유닛(Unit)의 이해

`systemd`는 관리하는 모든 대상을 **유닛(Unit)**이라는 단위로 취급합니다. 유닛 파일은 `/etc/systemd/system/` (사용자 정의 유닛) 또는 `/lib/systemd/system/` (패키지 설치 유닛) 디렉터리에 위치하며, `.service`, `.target`, `.timer`, `.mount` 등 다양한 유형이 있습니다.

### 서비스 유닛 (`.service`) 파일 구조

서비스 유닛 파일은 특정 데몬을 어떻게 시작하고, 중지하며, 관리할지를 정의합니다. 파일은 `[Unit]`, `[Service]`, `[Install]` 세 가지 주요 섹션으로 구성됩니다.

- **`[Unit]` 섹션**: 서비스에 대한 설명과 다른 유닛과의 의존 관계를 정의합니다.
    - `Description`: 유닛에 대한 설명.
    - `After`: 이 유닛이 시작되기 전에 시작되어야 할 다른 유닛을 지정합니다. (예: `After=network.target` -> 네트워크가 준비된 후에 시작)
    - `Wants`: `After`와 유사하지만, 의존하는 유닛이 실패하더라도 이 유닛은 시작을 시도합니다. (느슨한 의존성)
    - `Requires`: `After`보다 강력한 의존성. 의존하는 유닛이 활성화되지 않으면 이 유닛도 활성화되지 않습니다.

- **`[Service]` 섹션**: 서비스의 실제 동작을 정의합니다.
    - `Type`: 서비스의 프로세스 시작 유형을 지정합니다. (`simple`, `forking`, `oneshot` 등)
    - `ExecStart`: 서비스를 시작할 때 실행할 명령어를 지정합니다.
    - `ExecStop`: 서비스를 중지할 때 실행할 명령어를 지정합니다.
    - `ExecReload`: 설정을 다시 로드할 때 실행할 명령어를 지정합니다.
    - `User`, `Group`: 서비스를 실행할 사용자 및 그룹을 지정합니다.
    - `Restart`: 서비스가 실패했을 때 자동으로 다시 시작할지 여부를 결정합니다. (`always`, `on-failure` 등)

- **`[Install]` 섹션**: `systemctl enable` 명령을 통해 서비스를 활성화할 때의 동작을 정의합니다.
    - `WantedBy`: 이 유닛이 어떤 `target`에 속할지를 지정합니다. 일반적으로 GUI 환경에서는 `graphical.target`, CLI 환경에서는 `multi-user.target`을 사용합니다.

### 예시: 간단한 웹 서버 서비스 유닛 작성

- `/etc/systemd/system/my-web.service`
  ```ini
  [Unit]
  Description=My Simple Web Server
  After=network.target

  [Service]
  Type=simple
  User=www-data
  Group=www-data
  ExecStart=/usr/bin/python3 -m http.server 8000 --directory /var/www/my-web
  Restart=on-failure

  [Install]
  WantedBy=multi-user.target
  ```

- **유닛 파일 적용 및 시작**:
  ```bash
  # systemd가 새로운 유닛 파일을 인식하도록 함
  sudo systemctl daemon-reload

  # 서비스 시작
  sudo systemctl start my-web.service

  # 부팅 시 자동으로 시작되도록 활성화
  sudo systemctl enable my-web.service
  ```

## 2. 부팅 및 서비스 트러블슈팅

시스템 부팅이 안 되거나 특정 서비스가 제대로 시작되지 않을 때, `systemd` 관련 도구들은 문제 해결의 첫걸음이 됩니다.

### `systemctl`: 서비스 상태 확인

- **서비스 상태 확인**: 가장 먼저 확인할 명령어입니다. 서비스가 왜 실패했는지에 대한 핵심 로그와 상태 정보를 보여줍니다.
  ```bash
  systemctl status my-web.service
  ```
  - `Active: active (running)`: 정상 실행 중.
  - `Active: inactive (dead)`: 중지된 상태.
  - `Active: failed (Result: ...)`: 시작에 실패했으며, 실패 원인이 표시됩니다.

- **실패한 유닛 목록 확인**:
  ```bash
  systemctl --failed
  ```

### `journalctl`: 상세 로그 분석

`systemctl status`가 요약 정보를 보여준다면, `journalctl`은 더 상세한 전체 로그를 제공합니다.

- **특정 유닛의 전체 로그 보기**:
  ```bash
  journalctl -u my-web.service
  ```

- **부팅 과정 전체의 로그 보기**:
  ```bash
  journalctl -b
  ```
  ( `-b -1`은 이전 부팅, `-b -2`는 그 이전 부팅의 로그를 의미합니다.)

### `systemd-analyze`: 부팅 성능 분석

- **기능**: 시스템 부팅 과정에서 각 유닛이 얼마나 많은 시간을 소요했는지 분석하여 부팅 속도를 저하하는 원인을 찾는 데 도움을 줍니다.

- **주요 명령어**:
  ```bash
  # 전체 부팅 시간 요약
  systemd-analyze

  # 각 유닛별 부팅 시간 분석
  systemd-analyze blame

  # 부팅 과정의 순서와 시간 관계를 트리 형태로 시각화
  systemd-analyze critical-chain
  ```

### 디버깅 절차 요약

1.  **문제 현상 파악**: 부팅이 멈추는가? 특정 서비스만 실패하는가?
2.  **`systemctl status <unit>`**: 실패한 서비스의 상태와 요약 로그를 확인한다.
3.  **`journalctl -u <unit>`**: 해당 서비스의 상세 로그를 처음부터 끝까지 검토하여 에러 메시지를 찾는다. (설정 파일 오류, 권한 문제, 포트 충돌 등)
4.  **`journalctl -b`**: 부팅 과정 전반에 문제가 있다면, 부팅 로그를 확인하여 커널 메시지나 다른 서비스의 실패가 원인인지 확인한다.
5.  **`systemd-analyze`**: 부팅이 느리다면, 어떤 서비스가 병목 현상을 일으키는지 확인한다.
6.  **유닛 파일 수정**: 원인을 찾았다면, `/etc/systemd/system/` 아래의 유닛 파일을 수정한 후 `systemctl daemon-reload`를 실행하고 다시 서비스를 시작해본다.
