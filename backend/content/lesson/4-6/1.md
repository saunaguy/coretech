# 4-6-1: 네트워크 성능 측정: `iperf3`/`mtr`/`ping` 방법론

"네트워크가 느려요"라는 막연한 문제를 해결하기 위해서는, **지연 시간(Latency)**, **대역폭(Bandwidth)**, **패킷 손실(Packet Loss)**이라는 세 가지 핵심 지표를 객관적으로 측정하고 분석하는 방법론이 필요합니다. `ping`, `mtr`, `iperf3`는 이 세 가지 지표를 측정하는 데 사용되는 필수적인 도구입니다.

## 1. 지연 시간 (Latency) 측정

- **개념**: 패킷이 출발지에서 목적지까지 도달하는 데 걸리는 시간. RTT(Round Trip Time, 왕복 시간)으로 측정되는 경우가 많습니다. 지연 시간은 물리적인 거리, 중간에 거치는 네트워크 장비의 수와 성능에 영향을 받습니다.

### `ping`: 가장 기본적인 RTT 측정
- **방법론**: `ping`을 여러 번 실행하여 최소/평균/최대 RTT 값을 확인합니다. 평균값이 낮고, 최소값과 최대값의 차이(편차, Jitter)가 적을수록 안정적인 네트워크입니다.
  ```bash
  # 1초 간격으로 10번 ping 실행
  ping -c 10 google.com
  ```
  - **분석**: `time=... ms` 부분이 RTT를 나타냅니다. 만약 RTT 값이 간헐적으로 크게 튀는 현상이 보인다면, 네트워크 경로 어딘가에 간헐적인 혼잡이나 문제가 있음을 시사합니다.

### `mtr` (My Traceroute): 경로 전체의 지연 시간 분석
- **방법론**: `mtr`은 `ping`과 `traceroute`를 결합한 도구로, 목적지까지 거쳐 가는 모든 라우터(홉) 각각에 대한 RTT(Last, Avg, Best, Wrst)와 패킷 손실률(Loss%)을 지속적으로 보여줍니다.
  ```bash
  mtr google.com
  ```
  - **분석**: 특정 홉(라우터)에서부터 `Avg` RTT 값이 갑자기 급증한다면, 해당 홉 또는 그 다음 구간이 전체 지연 시간의 주요 원인임을 알 수 있습니다. 이를 통해 문제의 원인이 내 내부 네트워크인지, ISP 구간인지, 아니면 상대방 네트워크인지를 국소화(localize)할 수 있습니다.

## 2. 대역폭 (Bandwidth) 측정

- **개념**: 네트워크 경로를 통해 단위 시간당 전송할 수 있는 최대 데이터의 양. 보통 Mbps(Mega bits per second) 또는 Gbps로 표현됩니다.

### `iperf3`: 네트워크 최대 처리량 측정
- **기능**: `iperf3`는 두 지점(클라이언트와 서버) 간의 실제 네트워크 처리량(Throughput)을 측정하는 데 사용되는 표준 도구입니다. 한쪽을 서버 모드로 실행하고, 다른 쪽에서 클라이언트 모드로 접속하여 지정된 시간 동안 최대한 많은 데이터를 전송하며 성능을 측정합니다.

- **방법론**:
  1.  **서버 측 실행**:
      ```bash
      # iperf3 서버 모드로 실행 (-s)
      iperf3 -s
      ```
  2.  **클라이언트 측 실행**:
      ```bash
      # 10.0.0.1 서버로 10초 동안 테스트 실행
      iperf3 -c 10.0.0.1 -t 10

      # 양방향 동시 테스트 (-d)
      iperf3 -c 10.0.0.1 -d

      # UDP 테스트 (-u), 100Mbps 대역폭으로 지정
      iperf3 -c 10.0.0.1 -u -b 100M
      ```
- **분석**: 클라이언트의 결과에서 `Bitrate` 부분을 확인합니다. 이 값이 계약한 네트워크 대역폭(예: 1Gbps)에 현저히 미치지 못한다면, 네트워크 장비(스위치, 케이블)의 물리적 결함, 잘못된 설정(예: Half-duplex), 또는 경로상의 다른 병목 현상을 의심해 볼 수 있습니다.

## 3. 패킷 손실 (Packet Loss) 측정

- **개념**: 전송된 패킷 중 목적지에 도달하지 못하고 중간에 유실되는 패킷의 비율. 패킷 손실은 네트워크 혼잡, 하드웨어 오류, 잘못된 케이블링 등으로 인해 발생하며, 1%의 손실이라도 TCP 통신의 성능을 급격히 저하시키는 주요 원인이 됩니다.

### `ping`과 `mtr`을 이용한 측정
- **방법론**:
    - **`ping`**: `ping`을 장시간(예: 수백 회 이상) 실행하여 최종 통계에서 `packet loss` 비율을 확인합니다.
      `ping -c 100 [목적지_IP]`
    - **`mtr`**: `mtr`을 실행하여 `Loss%` 컬럼을 주시합니다. 특정 홉에서부터 패킷 손실이 지속적으로 발생한다면, 해당 라우터에 문제가 있을 가능성이 높습니다.

- **분석**: 0%가 아닌 패킷 손실은 어떤 경우에도 정상적인 상태가 아닙니다. 단, 일부 ISP 라우터는 보안상의 이유로 자신에게 들어오는 ICMP 패킷을 의도적으로 버리는 경우가 있으므로, 마지막 목적지에서의 손실률이 0%라면 중간 홉의 손실은 무시해도 되는 경우도 있습니다.

### 종합적인 성능 진단 방법론

1.  **`ping`으로 시작**: 목적지까지의 기본적인 연결성과 대략적인 RTT를 확인한다.
2.  **`mtr`로 심화**: 지연 시간이 길거나 간헐적인 끊김이 있다면, `mtr`을 사용하여 문제 구간이 어디인지(내부망, ISP, 외부망)를 특정한다.
3.  **`iperf3`로 검증**: 네트워크 장비 교체나 회선 증설 후, `iperf3`를 사용하여 실제 대역폭이 예상대로 나오는지 정량적으로 측정하고 검증한다.
4.  **지속적인 모니터링**: `ping`이나 `mtr`을 장시간 실행하여 간헐적으로 발생하는 패킷 손실이나 RTT 급증 현상이 있는지 확인한다.

이처럼 각 도구의 목적을 이해하고 체계적인 방법론에 따라 접근하면, 막연했던 네트워크 성능 문제를 구체적인 수치로 표현하고 원인을 논리적으로 추적해 나갈 수 있습니다.
