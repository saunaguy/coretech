# 4-6-3: 서비스 레벨 점검: `ss`/`curl`/`nmap`

네트워크의 물리적, 논리적 연결(L1-L4)이 정상임을 확인했더라도, 실제 애플리케이션 서비스(L7)가 제대로 동작하지 않을 수 있습니다. 서비스 레벨 점검은 애플리케이션이 예상대로 요청을 처리하고 올바른 응답을 주는지 확인하는 과정입니다. `ss`, `curl`, `nmap`은 이 과정을 돕는 핵심 도구입니다.

## 1. `ss`: 서비스가 LISTEN 하고 있는가?

- **기능**: `ss` (Socket Statistics)는 트러블슈팅의 가장 첫 단계로, 진단하려는 서비스가 서버에서 **예상하는 IP 주소와 포트에서 정상적으로 연결을 기다리는 상태(LISTEN)**에 있는지 확인하는 데 사용됩니다. (자세한 사용법은 `2-4-7` 참고)

- **점검 시나리오**: 웹 서버(nginx)에 접속이 안 된다.

- **점검 방법**:
  ```bash
  # 서버에서 실행
  sudo ss -tlpn | grep nginx
  ```
  - **정상적인 결과 예시**:
    `LISTEN  0  511  0.0.0.0:80   0.0.0.0:*  users:(("nginx",pid=1234,...))`
    - **분석**: `nginx` 프로세스가 모든 IP 주소(`0.0.0.0`)의 80번 포트에서 정상적으로 LISTEN 하고 있음을 의미합니다.

  - **비정상적인 결과 예시**:
    - **아무것도 출력되지 않음**: `nginx` 서비스가 아예 실행 중이 아니거나, 시작에 실패했을 가능성이 높습니다. (`systemctl status nginx`로 확인 필요)
    - `LISTEN  0  511  127.0.0.1:80   0.0.0.0:*`: `nginx`가 로컬호스트(`127.0.0.1`) 주소에만 바인딩되어 있습니다. 이 경우, 서버 외부에서는 절대 접속할 수 없습니다. (`nginx` 설정 파일에서 `listen` 지시어를 수정해야 합니다.)

## 2. `curl`: 애플리케이션이 올바르게 응답하는가?

- **기능**: `curl`은 실제 클라이언트(웹 브라우저 등)처럼 서버에 HTTP 요청을 보내고, 서버가 보낸 **응답 코드, 헤더, 본문**을 그대로 보여주어 애플리케이션 레벨의 동작을 확인하는 데 매우 강력한 도구입니다. (자세한 사용법은 `2-4-14` 참고)

- **점검 시나리오**: 웹 페이지에 접속하면 "502 Bad Gateway" 에러가 발생한다.

- **점검 방법**:
  ```bash
  # -I 옵션으로 헤더만 확인, -v 옵션으로 상세 과정 보기
  curl -Iv http://www.example.com
  ```
  - **분석**:
    - **HTTP 상태 코드 확인**: 응답의 첫 줄 `HTTP/1.1 502 Bad Gateway`를 통해, 로드밸런서나 리버스 프록시가 백엔드 서버로부터 올바른 응답을 받지 못했음을 알 수 있습니다. `200 OK`가 정상입니다.
    - **`Server` 헤더 확인**: `Server: nginx/1.20.1` 헤더를 통해, 내가 통신하고 있는 대상이 실제 백엔드 서버가 아닌 `Nginx` 리버스 프록시임을 알 수 있습니다. 이는 문제가 프록시와 백엔드 서버 간의 통신에 있음을 시사합니다.
    - **리다이렉션 확인**: `301 Moved Permanently` 또는 `302 Found` 상태 코드와 함께 `Location:` 헤더가 보인다면, 서버가 다른 주소로 리다이렉션을 시도하고 있음을 의미합니다. 리다이렉션 설정이 올바른지, 무한 루프에 빠지지는 않았는지 확인해야 합니다.

## 3. `nmap`: 방화벽이 포트를 막고 있는가?

- **기능**: `nmap`은 원격에서 특정 호스트의 어떤 포트가 열려 있는지(open), 닫혀 있는지(closed), 또는 방화벽에 의해 필터링되고 있는지(filtered)를 스캔하는 도구입니다. 클라이언트 입장에서 서버까지의 경로에 방화벽이 있는지, 있다면 어떤 포트를 허용하는지 확인하는 데 사용됩니다. (자세한 사용법은 `2-4-14` 참고)

- **점검 시나리오**: 서버에서는 `ss`로 확인 시 80번 포트가 분명히 LISTEN 중인데, 외부 클라이언트에서는 접속이 안 된다.

- **점검 방법**:
  ```bash
  # 외부 클라이언트에서 서버 IP로 실행
  nmap -p 80 [서버_IP_주소]
  ```
  - **결과 분석**:
    - **`80/tcp open http`**: 포트가 열려 있고 서비스가 응답합니다. 방화벽은 문제가 아니며, 애플리케이션 자체의 문제일 가능성이 높습니다.
    - **`80/tcp closed http`**: 포트에 접근은 가능하지만, 해당 포트에서 LISTEN 중인 서비스가 없습니다. 서버의 서비스가 중지되었거나 잘못된 포트에서 실행 중일 수 있습니다. (`ss` 결과와 교차 확인 필요)
    - **`80/tcp filtered http`**: `nmap`이 보낸 스캔 패킷에 대해 서버로부터 아무런 응답이 없습니다. 이는 서버 앞단의 네트워크 방화벽이나 서버 자체의 방화벽(`firewalld`, `iptables`)이 해당 포트로의 접근을 차단(DROP)하고 있을 가능성이 매우 높습니다.

### 종합적인 서비스 레벨 점검 절차

1.  **(서버 내부)** `ss -tlpn`으로 서비스가 올바른 IP/포트에서 **LISTEN**하고 있는지 확인한다.
2.  **(서버 내부)** `curl localhost:[포트]`로 서버 내부에서 자기 자신에게 요청을 보내 애플리케이션이 최소한의 응답은 하는지 확인한다.
3.  **(외부 클라이언트)** `nmap -p [포트] [서버_IP]`로 클라이언트와 서버 사이의 **방화벽**이 포트를 막고 있지 않은지 확인한다. (`filtered` 상태 확인)
4.  **(외부 클라이언트)** `curl -Iv [서버_주소]`로 실제 **HTTP 응답**이 정상적인지(상태 코드, 헤더 등) 확인한다.

이처럼 내부에서 외부로, 낮은 계층에서 높은 계층으로 단계적으로 점검 범위를 넓혀가면, 복잡한 서비스 장애 문제의 원인을 체계적으로 찾아낼 수 있습니다.
