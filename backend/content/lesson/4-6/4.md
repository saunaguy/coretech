# 4-6-4: 네트워크 병목 분류 절차: 링크/전송/네트워크/애플리케이션

"네트워크가 느리다"는 문제는 하나의 원인으로 발생하지 않습니다. 케이블 문제부터 애플리케이션 코드의 비효율성까지, 다양한 계층에 걸쳐 원인이 존재할 수 있습니다. 효과적인 트러블슈팅을 위해서는 문제를 **계층별로 분류**하고, 각 계층에 맞는 진단 도구를 사용하여 원인의 범위를 체계적으로 좁혀나가는 접근 방식이 필요합니다.

## 1. 링크 계층 (L2) 병목: 물리적 연결의 문제

- **의심 증상**: 특정 장비만 네트워크가 간헐적으로 끊기거나, 대용량 파일 복사 시 속도가 현저히 느리다. `ping` 테스트 시 패킷 손실이 발생한다.
- **핵심 질문**: "케이블과 스위치 포트는 정상인가? 속도와 이중화 모드는 올바르게 협상되었는가?"

- **진단 절차 및 도구**:
    1.  **물리적 확인**: 서버와 스위치의 네트워크 케이블이 제대로 연결되어 있는지, 링크 LED가 정상적으로 점등되어 있는지 육안으로 확인합니다.
    2.  **`ip link` 또는 `ethtool`**: 인터페이스의 상태를 확인합니다.
        ```bash
        ip link show eth0
        # "LOWER_UP" 또는 "UP" 상태인지 확인

        ethtool eth0
        ```
        - `ethtool` 결과에서 `Speed`와 `Duplex` 항목을 확인합니다. `Speed: 1000Mb/s`, `Duplex: Full`과 같이 예상되는 최대 성능으로 설정되어 있는지 확인합니다. 만약 `100Mb/s`나 `Half-duplex`로 잘못 협상되었다면, 케이블 불량이나 스위치 포트 설정 오류를 의심할 수 있습니다.
    3.  **에러 카운트 확인**: `ip -s link show eth0` 또는 `ifconfig`의 `RX packets`, `TX packets` 대비 `errors`, `dropped` 카운트가 비정상적으로 증가하는지 확인합니다. 에러 카운트가 계속 증가한다면 물리적인 링크(케이블, NIC, 스위치 포트)에 문제가 있을 가능성이 높습니다.

## 2. 네트워크/전송 계층 (L3/L4) 병목: 경로와 패킷 손실의 문제

- **의심 증상**: 특정 목적지(IP 또는 도메인)에만 접속이 느리거나 실패한다. `ping` RTT(지연 시간)가 비정상적으로 높거나 변동이 심하다.
- **핵심 질문**: "패킷이 목적지까지 가는 경로에 문제는 없는가? 중간에 패킷 손실이 발생하지는 않는가?"

- **진단 절차 및 도구**:
    1.  **`ping`**: 목적지까지의 기본적인 RTT와 패킷 손실률을 측정하여 문제의 존재 여부를 확인합니다.
    2.  **`mtr`**: `ping`에서 지연이나 손실이 확인되면, `mtr`을 사용하여 어느 라우터(홉) 구간에서 문제가 발생하는지 특정합니다. 내부망 구간인지, ISP 구간인지, 아니면 상대방의 네트워크 구간인지를 파악하는 것이 중요합니다.
    3.  **`iperf3`**: `mtr`로 확인된 문제 구간의 양 끝단에서 `iperf3`를 실행하여, 해당 구간의 실제 최대 대역폭을 측정하고 병목 지점임을 재확인합니다.
    4.  **방화벽/ACL 확인**: `iptables`, `nftables`, `firewalld` 설정을 확인하여, 특정 프로토콜이나 포트의 트래픽을 의도치 않게 차단(drop)하거나 속도를 제한(rate limit)하는 규칙이 있는지 검토합니다.

## 3. 애플리케이션 계층 (L7) 병목: 서비스 자체의 문제

- **의심 증상**: 네트워크 경로(L2-L4)는 정상이지만, 특정 서비스(예: 웹사이트)의 응답이 느리다. `curl` 요청 시 TTFB(Time To First Byte)가 길게 측정된다.
- **핵심 질문**: "애플리케이션 서버가 요청을 처리하고 응답을 생성하는 데 시간이 오래 걸리는가?"

- **진단 절차 및 도구**:
    1.  **`curl` 상세 분석**: `curl`의 `-w` 옵션을 사용하여 요청의 전체 과정에 걸리는 시간을 단계별로 측정합니다.
        ```bash
        curl -o /dev/null -s -w "dnslookup: %{time_namelookup}\nconnect: %{time_connect}\nappconnect: %{time_appconnect}\npretransfer: %{time_pretransfer}\nstarttransfer: %{time_starttransfer}\ntotal: %{time_total}\n" [URL]
        ```
        - `time_connect`: TCP 연결 완료까지의 시간.
        - `time_starttransfer`: 서버가 응답 데이터의 첫 바이트를 보내기 시작할 때까지의 시간 (TTFB). 이 값이 길다면, 서버의 애플리케이션이 요청을 처리하는 데 시간이 오래 걸린다는 의미입니다.
    2.  **서버 자원 확인**: `top`, `htop`, `vmstat` 등의 도구를 사용하여, 요청 처리 중에 서버의 CPU, 메모리, 디스크 I/O가 병목 상태에 빠지는지 확인합니다.
    3.  **애플리케이션 로그 분석**: 애플리케이션의 접근 로그(access log)와 에러 로그(error log)를 확인하여, 특정 요청에 대한 처리 시간이 비정상적으로 길거나, 데이터베이스 쿼리 오류, 백엔드 API 호출 실패 등의 에러가 발생하는지 확인합니다.
    4.  **패킷 캡처 분석**: `tcpdump`로 패킷을 캡처하고 Wireshark로 분석하여, 애플리케이션이 비효율적인 통신 패턴(예: 불필요한 요청 반복)을 보이는지, 또는 TCP 레벨의 문제(예: 재전송, Zero Window)가 발생하는지 심층적으로 분석합니다.

네트워크 병목 분석은 이처럼 **Top-Down (애플리케이션 → 링크)** 또는 **Bottom-Up (링크 → 애플리케이션)** 방식으로 계층을 넘나들며, 각 단계에서 의심되는 가설을 세우고 적절한 도구를 통해 검증해나가는 과학적인 과정입니다.
