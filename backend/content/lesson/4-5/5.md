# 4-5-5: 컨테이너 네트워킹: 네임스페이스, veth, 브리지

도커(Docker)와 같은 컨테이너 기술은 애플리케이션을 격리된 환경에서 실행할 수 있게 해줍니다. 이러한 **격리(Isolation)**의 핵심 기술 중 하나가 바로 **리눅스 네임스페이스(Linux Namespaces)**이며, 특히 **네트워크 네임스페이스(Network Namespace)**는 컨테이너가 자신만의 독립적인 네트워크 환경을 가질 수 있게 해주는 기반이 됩니다.

## 1. 네트워크 네임스페이스 (Network Namespace)

- **개념**: 네트워크 네임스페이스는 각 컨테이너에게 자신만의 독립적인 네트워크 스택(Network Stack)을 제공하는 커널 기능입니다. 이는 다음을 포함합니다.
    - **독립적인 네트워크 인터페이스**: 각 네임스페이스는 자신만의 `lo`(루프백) 인터페이스와 `eth0` 같은 네트워크 인터페이스를 가질 수 있습니다.
    - **독립적인 라우팅 테이블**: 각 네임스페이스는 자신만의 라우팅 규칙을 가집니다.
    - **독립적인 `iptables` 규칙**: 각 네임스페이스는 자신만의 방화벽 규칙을 가질 수 있습니다.
    - **독립적인 포트 공간**: A 네임스페이스의 80번 포트와 B 네임스페이스의 80번 포트는 서로 다른 포트입니다.

- **결과**: 컨테이너는 마치 별개의 운영체제처럼, 호스트 시스템이나 다른 컨테이너와 충돌 없이 자신만의 IP 주소, 라우팅, 포트를 사용할 수 있게 됩니다.

## 2. 가상 네트워크 장치: `veth`와 `bridge`

격리된 네트워크 네임스페이스(컨테이너)가 외부 세계(호스트 및 다른 네트워크)와 통신하기 위해서는 이들을 연결해 줄 방법이 필요합니다. 이때 가상 네트워크 장치인 `veth`와 `bridge`가 사용됩니다.

### `veth` (Virtual Ethernet) 페어
- **개념**: `veth`는 항상 쌍(pair)으로 생성되는 가상의 이더넷 케이블과 같습니다. 한쪽 끝(`veth_A`)을 컨테이너의 네트워크 네임스페이스 안에 넣고, 다른 한쪽 끝(`veth_B`)을 호스트의 기본 네임스페이스에 두면, 두 네임스페이스 간에 데이터를 주고받을 수 있는 파이프라인이 생성됩니다.
- **동작**: `veth_A`로 들어온 패킷은 즉시 `veth_B`로 나오고, `veth_B`로 들어온 패킷은 `veth_A`로 나옵니다.

### 리눅스 브리지 (Linux Bridge)
- **개념**: 리눅스 브리지는 여러 개의 네트워크 인터페이스를 하나로 묶어주는 가상의 L2 스위치(Switch)처럼 동작합니다. 브리지에 연결된 인터페이스들은 모두 동일한 네트워크 대역에 속하게 되며, 서로 간에 통신할 수 있습니다.

## 3. 도커(Docker)의 기본 브리지 네트워크 구성

도커를 설치하면, 이러한 기술들을 사용하여 `docker0`라는 기본 브리지 네트워크를 자동으로 생성합니다. 컨테이너를 생성할 때 별도의 네트워크 옵션을 주지 않으면, 컨테이너는 이 `docker0` 브리지에 연결됩니다.

- **구성 과정**:
    1.  **`docker0` 브리지 생성**: 도커 데몬은 호스트 시스템에 `docker0`라는 이름의 리눅스 브리지를 생성하고, 여기에 IP 주소(보통 `172.17.0.1/16`)를 할당합니다. 이 브리지는 컨테이너들의 게이트웨이 역할을 합니다.
    2.  **컨테이너 생성**: `docker run` 명령으로 새 컨테이너를 생성합니다.
    3.  **네트워크 네임스페이스 생성**: 도커는 이 컨테이너를 위한 고유한 네트워크 네임스페이스를 생성합니다.
    4.  **`veth` 페어 생성**: `veth` 페어(`veth_A`, `veth_B`)를 생성합니다.
    5.  **컨테이너에 인터페이스 연결**: `veth_A`의 이름을 `eth0`로 바꾸고, 컨테이너의 네트워크 네임스페이스 안으로 이동시킵니다. 그리고 이 `eth0`에 `docker0` 대역의 IP 주소(예: `172.17.0.2`)를 할당합니다.
    6.  **호스트에 인터페이스 연결**: 나머지 `veth_B`를 호스트의 `docker0` 브리지에 연결(attach)합니다.

- **통신 흐름**:
    - **컨테이너 → 외부**: 컨테이너(`172.17.0.2`)에서 외부(예: `google.com`)로 나가는 패킷은 자신의 게이트웨이인 `docker0` 브리지(`172.17.0.1`)로 향합니다. 호스트는 이 패킷을 받아 `iptables`의 `MASQUERADE`(SNAT) 규칙에 따라 출발지 IP를 컨테이너의 IP에서 호스트의 공인 IP로 바꾸어 외부로 내보냅니다.
    - **외부 → 컨테이너**: `docker run -p 8080:80`과 같이 포트 포워딩을 설정하면, 도커는 호스트의 `iptables`에 DNAT 규칙을 추가합니다. 외부에서 호스트의 8080번 포트로 들어온 패킷은 이 규칙에 따라 목적지 IP와 포트가 컨테이너의 IP와 80번 포트(`172.17.0.2:80`)로 변경되어 `docker0` 브리지를 통해 컨테이너에게 전달됩니다.

이처럼 컨테이너 네트워킹은 리눅스 커널이 제공하는 네임스페이스, `veth`, 브리지, `iptables`와 같은 기본적인 기능들을 정교하게 조합하여, 격리되어 있으면서도 외부와 원활하게 통신할 수 있는 가상의 네트워크 환경을 만들어내는 기술입니다. 쿠버네티스(Kubernetes)와 같은 컨테이너 오케스트레이션 시스템은 이러한 기본 원리 위에서 훨씬 더 복잡하고 동적인 네트워크 정책을 구현합니다.
